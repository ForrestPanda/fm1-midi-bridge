# AC79 SDK notes (tag AC79NN_SDK_V1.2.1_2023-12-13)

Findings from reading the SDK tree on 2026-10-11. Paths are relative to the SDK root.

## Build on Linux

Works with the toolchain Felucca's `tools/get_toolchain.sh` installs (clang 4.0.1 for
pi32v2 in `~/.jieli/toolchain/pi32v2/bin`). The SDK Makefiles expect
`/opt/jieli/pi32v2/bin`; override on the command line:

```
ulimit -n 8192
cd apps/demo/demo_ble/board/wl82
make TOOL_DIR=$HOME/.jieli/toolchain/pi32v2/bin -j8
```

Output: `cpu/wl82/tools/sdk.elf`. The post-build step (`cpu/wl82/tools/download.sh`)
fails on Linux: it calls `/opt/utils/strip-ini` and `host-client`, JieLi-internal tools
that upload the ELF to a packaging server. The Windows flow in `download.c` shows what
they do:

```
objcopy -O binary -j .text sdk.elf text.bin
objcopy -O binary -j .data sdk.elf data.bin
objcopy -O binary -j .ram0_data sdk.elf ram0_data.bin
objcopy -O binary -j .cache_ram_data sdk.elf cache_ram_data.bin
cat text.bin data.bin ram0_data.bin cache_ram_data.bin > app.bin
isd_download.exe isd_config.ini -tonorflash -dev wl82 -boot 0x1c02000 -div1 \
    -uboot uboot.boot -app app.bin cfg_tool.bin -res cfg ...   -> jl_isd.fw
fw_add.exe -fw jl_isd.fw -add ota.bin -type 100                 -> adds the loader
ufw_maker.exe -fw_to_ufw jl_isd.fw                              -> update.ufw
```

So `app.bin` is just four sections concatenated, and the rest (flash head, JLFS
entries, SFC encryption with the chip key, UFW container) is what Felucca's
`tools/fm1pkg_make.py` re-creates for the FM-1. Our packager does the same.

App entry: `ENTRY=0x2000120` (SFC/XIP mode; `isd_config_rule.c`), consistent with the
FM-1 app area at flash 0x4000 mapping to CPU 0x02000000 and `app_area_head` at
0x02000120.

The demo app config (`apps/demo/demo_ble/include/app_config.h`) assumes a 4 MB flash
and optional SDRAM; the FM-1 has 1 MB and 512 KB RAM, so `__FLASH_SIZE__` must be
1 MB and `__SDRAM_SIZE__` 0.

## Update framework (`cpu/wl82/liba/update.a`, headers in `include_lib/update/`)

- Closed library, source glue in `apps/common/update/update.c`.
- A transport is an `update_op_api_t` with `ch_init`, `f_open`, `f_read`, `f_seek`,
  `f_stop`, `notify_update_content_size`, `ch_exit`. `apps/common/update/uart_update.c`
  (source) implements one over UART: the library *pulls* the package through
  `f_seek`/`f_read`. That is exactly the shape of the M-VAVE protocol, where the device
  sends cmd `0x30` read requests and the host answers. A `midi_update.c` modelled on
  `uart_update.c` whose `f_read` sends a read request over USB-MIDI SysEx and waits
  for the answer should give us step 1 with vendor code.
- Flow: `update_mode_api_v2(UART_UPDATA, priv_param_fill, before_jump)` ->
  the library reads the UFW header, finds the loader file (`ota.bin`, name
  `JL_OTA_LOADER_FILE_NAME`), checks its head CRC (`UPDATE_RESULT_LOADER_HEAD_CRC_ERR`
  "check that the bytes before ota.bin are 00"), writes it to the loader area it
  computes from the VM/reserved layout (`calc_loader_area_info`, `loader_saddr`),
  writes `UPDATA_PARM` (magic 0x5441, type, result UPDATA_READY, `ota_addr`), and
  resets. The SPL runs the loader.
- Strings in `update.a` show it looks for `flash.bin`, `ota.bin`, checks chip name
  (`AC791N`), product id, uboot match, flash encryption key.
- Stock FM-1 loader `usb_hid_ota.bin` is 0x4DE1 bytes; nothing in the SDK tools has
  that size (`ota.bin` 272727, `usb_update2.bin` 23200, `sd_update2.bin` 23452), so it
  is an M-VAVE-specific loader. The loader we ship decides step 2's transport; see
  `update-protocol.md`.

## BLE (`cpu/wl82/liba/btstack.a` + `btctrler.a`, source glue in `apps/common/ble/`)

- `apps/common/ble/le_trans_data.c` is the GATT server template (enabled by
  `TRANS_DATA_EN` in the demo config): advertising, connection, MTU, `att_read_callback`
  / `att_write_callback`, `app_send_user_data()` for notifications, connection parameter
  requests (`ble_op_conn_param_request`), bonding (`TCFG_BLE_SECURITY_EN`).
- The ATT database is a BTstack-style byte array `profile_data[]` in
  `apps/common/ble/include/le_trans_data.h`, "generated by jieli gatt_inc_generator.exe"
  (format: size16, flags16, handle16, uuid, value). We can write the BLE MIDI one by
  hand or with BTstack's `compile_gatt.py` (BSD) from a `.gatt` file: one 128-bit
  primary service, one 128-bit characteristic READ | WRITE_WITHOUT_RESPONSE | NOTIFY |
  DYNAMIC, and its CCCD.
- BLE central (host mode) is also there: `le_net_central.c`, `BT_NET_CENTRAL_EN`.
- Demo config: `TCFG_USER_BLE_ENABLE 1`, `TCFG_USER_BT_CLASSIC_ENABLE 0`.

## USB device (`apps/common/usb/device/`, driver in a lib)

- Composite device assembled in `usb_device.c` from class flags (MSD, UAC audio,
  HID, custom HID, CDC, UVC, printer) each providing `*_desc_config()` and endpoint
  handlers. **No MIDI class.** `include_lib/driver/device/usb/device/uac_audio.h` has
  the MIDI streaming descriptor constants (`USB_SUBCLASS_MIDISTREAMING`,
  `UAC_MIDI_IN_JACK`, `UAC_MIDI_OUT_JACK`), unused.
- Template for a new class: `hid.c` (`hid_desc_config`, `hid_endpoint_init`,
  `hid_itf_hander`, `hid_intrtx` / `hid_intrrx`, `hid_tx_data`, `hid_register`).
  A MIDI class is one AudioControl interface (empty) + one MIDIStreaming interface
  with one bulk IN and one bulk OUT endpoint, 4-byte event packets.
- Default VID 0x3654 (JieLi). The stock FM-1 VID/PID are unknown until we have one.

## UART (TRS MIDI IN)

`include_lib/driver/cpu/wl82/asm/uart_dev.h`: `uart_open(&(struct uart_platform_data_t){
.tx_pin = -1, .rx_pin = IO_PORTH_08, .baud = 31250, .rx_cbuf = buf, .rx_cbuf_size = 2^n,
.frame_length, .rx_timeout, .isr_cbfun })`. The driver picks a free UART and remaps the
pin. Felucca uses UART1 with PH8 through input channel 1; the SDK driver should do the
same remap by itself.

Not used by the bridge since 2026-10-14 (`app/trs_uart.c` drives UART1 directly, Felucca's
way). What the device did in fm1-emu: `dev_read` with `UART_SET_RECV_BLOCK 1` pends on the
driver's own semaphore (`_uartx_recv` -> `os_sem_pend`), which only the UART interrupt
posts, so `UART_SET_RECV_TIMEOUT` does not make it return on a silent line (it is the
silence *after* bytes that ends a read); with `UART_SET_RECV_BLOCK 0` the read returned
nothing even with bytes in the ring; and a task parked in that blocking read seemed to
make the SDK's two-core scheduler stall at boot (that was the emulator: its hardware
lock ignored the SDK's `lockset`, see `docs/plan.md`). The ioctls, from
`include_lib/driver/device/uart.h`: RECV_BLOCK,
RECV_TIMEOUT (ms), RECV_TIMEOUT_CB, GET_RECV_CNT, CIRCULAR_BUFF_ADDR/LENTH, START.

## Flash layout

`cpu/wl82/tools/isd_config_rule.c` is the packer's rule file (VM, BTIF, USER, LOG
regions, `BR22_TWS_VERSION`, `VM_OPT`). Our packager writes the JLFS entries instead,
and the app discovers regions from the flash head at runtime. Keep the FM-1 head
untouched: SPL and `isd_config.ini` (chip key) live there.
